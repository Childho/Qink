# ADR-0009：数据耐久三件套（原子写 / 坏档留证 / 退出冲刷）

日期：2026-10-09

## 背景

2026-10-09 产品×工程审查（`docs/review/06-product-audit-2026-10.md`）确认了产品唯一的「存在级」风险链：

1. **落盘非原子**：`persist()` 直接 `writeFile` 覆写 `data.json`，断电/崩溃可能留下写了一半的截断文件；
2. **坏档静默清零**：主文件与备份都解析失败时，落入 `defaultData()` 且启动即 `queueSave()` 把空数据**覆盖写回两个文件**——没有提示、没有留证，用户全年目标与归档无声蒸发且现场被销毁（P0）；
3. **退出丢最后 300ms**：`before-quit` 只置 `isQuitting` 标志，防抖窗口内挂起的最后一次修改（比如刚输完一条任务就点托盘退出）随进程消亡。

Qink 承诺「本地数据、无账号、无云端」，本地可靠性是产品能力本身，不是工程细节。

## 决策

持久化核心抽到 `src/main/store-io.ts`（不依赖 electron、路径注入，vitest 直测）；`store.ts` 退化为接线层。

- **原子写**：两份文件（主 + AppData 备份）一律「写 `.tmp` → `fsync` → `rename` 顶替」。崩溃/断电的结果只有旧文件或新文件两种，永远不会出现半写文件——半写文件正是旧恢复链静默清零的入口。`.tmp` 残留由下次保存覆写自愈。
- **坏档留证**：文件存在但读不出/不是 JSON 对象（含权限异常）→ 改名 `<file>.corrupt` 保住现场，然后走下一恢复源（主→备→空白）。**双坏时弹原生对话框**告知用户「已从空白开始 + 坏档位置」，可手动抢救。首次运行（ENOENT）不算坏档，不打扰。同名 `.corrupt` 已存在时被最新坏档替换（只保最新现场）。
- **退出冲刷**：`before-quit` 同步冲刷挂起的防抖写（同步版原子写）。托盘退出与渲染层退出都经 `app.quit()` → `before-quit`，覆盖全部显式退出路径。

否决的替代方案：继续 `writeFile` 直写靠备份兜底——备份与主文件同一次 persist 写入、内容恒同，主文件被半写截断时备份虽在，但旧的「双坏即清零」路径仍在（本次要拆的就是它）；A/B 轮换文件 + 指针文件——多一份状态要维护，收益不高于 tmp+rename；SQLite/WAL——对一个明文 JSON 承诺过重；退出时 `preventDefault` + 异步落盘再 `quit()`——引入二次退出时序复杂度，同步冲刷三行解决。

## 代价与边界

- 每次落盘多一次 `fsync`（毫秒级，防抖 300ms 合并后无感）；Windows 目录级 fsync 不可用，极极端的「rename 后断电、目录项未刷」在 NTFS 上理论存在，接受。
- **Windows 强制关机/注销**不保证触发 `before-quit`：该场景等同断电，由原子写兜底——文件不会坏，最多丢最后 300ms 的修改且重启后内容自洽。
- 坏档判定不含 schema 校验（`version` 迁移、字段级校验是另一件事，审查列为 P2 另案）：本 ADR 只承诺「读得出 = 不销毁，读不出 = 留证」。
- dev / 正式 / 便携版共享同一 `data.json` 且单实例锁按 userData 隔离的双开互覆问题（P2）不在本 ADR 范围。

## 验证

`tests/store.test.ts` 10 例：恢复链全分支（首启 / 主坏备好 / 主缺备好〔M4 真实事故〕/ 双坏双留证 / 非对象 JSON）、坏档内容逐字保留、防抖窗口内不落盘且合并为最后一次、双写内容一致、rename 顶替旧文件、无 `.tmp` 残留、退出冲刷同步完成且清定时器、无挂起时零动作。`npm test` 62/62 ✅ · `npm run typecheck` 零错误 ✅ · `npm run build` ✅。`index.ts` 的接线（双坏弹窗、before-quit 冲刷）经 typecheck 与代码走查；完整运行态验证待下次打包装机时随真实数据首启走一遍（装机前现有 data.json 由旧版写入、格式合法，新版读取即走 source: 'main' 正常路径）。
