# 性能审查

> 先说结论：对这个体量的桌面常驻应用，性能现状是**健康的**——启动链路短、空闲时几乎零开销、动画全部走合成器友好属性、高频操作有节流/合帧/防抖三件套。真正的性能储备压力点只有两个：碎裂动画的瞬时 DOM 量，以及归档无限增长后的翻日扫描。两者在可预见的使用年限内都不构成问题。

## 实测数据

| 指标 | 数值 | 评价 |
| --- | --- | --- |
| 运行中内存（已安装版，4 进程合计） | 约 325MB | Electron 应用的正常水位（Chromium 渲染引擎的固定成本约 200MB 起），空依赖策略已把可省的省了 |
| `npm test` | 224ms / 34 个测试 | 快，说明纯逻辑层没有隐藏的重计算 |
| 依赖数（运行时 dependencies） | **0 个** | `package.json` 里只有 devDependencies——d3-delaunay 已随 Voronoi 方案一起移除，碎裂几何全部自算（`shatter.ts`），安装包和内存都不背无用库 |

## 启动路径

`index.ts:40-49`：`loadData()`（读一个 JSON）→ `queueSave()` 立即落盘自愈 → 建窗 → 托盘 → IPC。没有网络请求、没有多文件扫描，链路是短的。渲染层 `boot()`（`main.ts:1074`）一次 `getData` 后同步渲染。启动即用持久化尺寸建窗避免跳变（`index.ts:64` 的注释记录了为什么这么做）。**没有可挑的毛病。**

## 空闲开销

常驻的周期性活动只有三个：

1. 跨午夜对表定时器，30 秒一次（`main.ts:818`）——一次只是比较一个日期字符串，可忽略；
2. 数据防抖保存的 300ms 定时器（`store.ts:51`）——仅在有变更时存在；
3. 窗口 `move` 事件监听（`index.ts:100`）——只在移动时触发。

没有轮询、没有后台网络、没有常驻动画。**空闲 CPU 接近零**，作为常驻桌面工具这是底线，守住了。

## 动画与渲染

**做对了的：**

- 碎片动画用 WAAPI（浏览器原生动画接口）只动 `transform` 和 `opacity`（`shatter.ts:258`）——这两个属性由 GPU 合成器处理，不触发重排/重绘，是 Web 动画的黄金组合。
- `will-change` 只用在 `.shard`（`style.css:368`）——这个属性会强制浏览器为元素开独立合成层，滥用反而费内存，这里克制得对。
- 归档渲染做了"三阶段批量读写"：先全部建行进 DOM → 一次性读尺寸（单次回流）→ 再写裂纹 SVG（`archive.ts:325-353`，注释详细解释了为什么逐行交错读写会造成布局抖动）。这是超出常见水准的手工优化。
- 尺寸上报用 rAF 合帧 + 字符串去重（`main.ts:91-102`），内容变化时不会逐帧轰炸主进程。

**压力点与量级推算：**

1. **完成单条任务**：一行拆成 9 条放射线 × 3 环 ≈ 27 个碎片 DOM，每个是一次行克隆 + clip-path 裁切（`shatter.ts:229-268`），持续约 0.4–0.6 秒。单次量级无感。
2. **打开归档**：入场碎片合并动画上限 10 行（`archive.ts:9` 的 `ANIMATE_ROW_CAP`），每行 8–9 条放射线 × 3 环 ≈ 24–27 片，**峰值约 240–270 个并发动画元素**，且每个碎片是 `cloneNode(true)` 深拷贝——行里如果已带裂纹 SVG，SVG 也被完整拷贝。中端机无压力；低端机（老核显/无独显）可能掉一次帧。已有的 10 行上限就是为这个设的，超过的行退化为 180ms 淡入（`archive.ts:364`）。**可选优化**：克隆时移除 `.cracks` 子节点（碎片飞行中裂纹细节肉眼不可辨），能把每个碎片的节点数砍一半以上。属锦上添花。
3. **退出归档的反向碎开**：同样上限 10 行并行（`archive.ts:116-119`），量级同上。

## 进程间通信（IPC）

这是 Electron 特有的开销面——渲染层和主进程之间每次通信都有序列化成本。审查了全部高频路径：

| 路径 | 频率 | 防护措施 | 评价 |
| --- | --- | --- | --- |
| 拖动位移上报 `drag-move` | 每帧（≤60 次/秒） | rAF 合帧（`main.ts:871`），主进程锚点式定位不累加 | 标准做法，无可挑剔 |
| 位置回传 `win-pos` | 16ms 节流（`index.ts:128`） | 有节流 | **微优化空间**：回传只服务悬浮球换边判断（`main.ts:65`），贴纸形态下渲染层只存值不用，可在贴纸形态停发 |
| 尺寸上报 `note-resize` | 内容变化时 | rAF + `lastSentSize` 去重（`main.ts:97`） | 防护充分 |
| 数据落盘 `data:set` | 每次编辑操作 | 全量 JSON 一次 IPC + 主进程 300ms 防抖合并写盘（`store.ts:51`） | 数据量小（见下），全量发送是正确的简单方案 |

**数据量推算**：一条任务约 100 字节，重度用户每天 30 条 × 用 5 年 ≈ 5MB JSON。每次 `setData` 全量序列化 5MB 会有可感知的卡顿吗？序列化本身在毫秒级，且只在编辑操作时发生（不是每帧），**到那个量级前都不需要改增量同步**。这是"简单方案用对地方"的正面例子。

## 内存增长的长期曲线

- 归档数组无限增长（这是产品语义——永久存档，规格如此）。加载时整个 JSON 进内存，5MB 量级完全无压力。
- 碎片 DOM 全部在动画结束后 `remove()`（`shatter.ts:264,276`），有 900ms 兜底定时器防隐藏窗口时 onfinish 不触发导致的泄漏（`shatter.ts:275`，这个兜底的注释说明作者踩过 WAAPI 的坑）。**没有发现 DOM 泄漏路径。**
- 事件监听器：归档的 document 级监听在关闭时成对移除（`archive.ts:112-114`），任务行监听随行销毁。干净。

## 布局性能

- `desiredNoteHeight()`（`main.ts:86`）读 `scrollHeight/clientHeight` 触发强制回流，但被 rAF 合帧成每帧最多一次，且只在内容/尺寸变化时进入调度。可接受。
- FLIP 排序动画里有一次刻意的 `getBoundingClientRect()` 强制回流来"锁"起始位移（`main.ts:410`，有注释），这是 FLIP 技术的标准写法。
- CSS 上 `transition` 明确列出了属性而非 `all`（`style.css:203` 有注释解释），避免了无关属性参与过渡计算。

## 性能篇结论与建议汇总

| 优先级 | 建议 | 理由 |
| --- | --- | --- |
| P3 | 碎片克隆时剥掉 `.cracks` 子树 | 归档打开的峰值动画元素数减半，低端机体验保险 |
| P3 | 贴纸形态下停发 `win-pos` 回传 | 每次窗口移动省一路无用 IPC，改动一行量级 |
| 不动 | 数据全量同步、归档全量扫描 | 在可预见年限内量级都不构成问题，提前优化是负收益 |
