# 测试与工程化审查

> 结论：测试策略方向正确——把"错了会静默污染数据"的纯逻辑全部圈进了单测（34 个，224ms 跑完），且边界用例选得老练。缺口同样清晰：**渲染层 1088 行交互逻辑零自动化覆盖**，工程链路上缺 lint 和 CI 这两道廉价防线。

## 测试现状

```
tests/dates.test.ts    11 个  周期键（含 ISO 周跨年边界）、滚入判定、目标失效
tests/window.test.ts    9 个  宽高钳制边界、位置钳制、双形态尺寸
tests/shatter.test.ts   5 个  多边形裁剪、碎片覆盖完整性（并集罩住矩形）
tests/tasks.test.ts     9 个  三层分区排序、拖动重排的分区钳制
```

本次审查实测：**34 个全部通过，耗时 224ms**。

**用例质量抽查（挑几个说明水准）：**

- `dates` 测了 ISO 周年的经典陷阱日期（年末年初跨年周），这是日历代码最容易错的地方；
- `shatter` 测了"碎片并集必须罩住整个矩形"——这是碎裂视觉不出现空洞的不变量，把它写成断言而不是靠肉眼验收，是聪明做法；
- `tasks` 测了分区钳制的边界（拖到别区门口被钳回），与 UI 让位预览的语义对齐。

这套测试的价值密度很高：测的都是**纯函数 + 数据不变量**，不测 DOM 快照（那种测试脆且贵）。

## 缺口分析

### P2-7 渲染层零覆盖——当前最大的质量风险面

未覆盖的高危逻辑（都在 `renderer/src/main.ts`）：

1. **行内编辑状态机**（startGoalEdit/startTaskEdit）：`finished` 防重入、Enter/Escape/blur 三路竞争——改错一处就是"回车丢字"或"Esc 后再点开还是编辑态"；
2. **拖动排序**（wireTaskDrag）：快照/让位/落位/取消四条路径，还有 landingTimer 与下一次拖动的互斥；
3. **双击/单击判定**：EDIT_DELAY_MS 与系统双击窗的竞态（UX 篇 P1-2 的死区问题正说明这段逻辑没有护栏）；
4. **composer 草稿保留/恢复**、**归档手势的路径累积判定**（HOLD_MS × WIGGLE_PATH_PX 组合）。

这些逻辑的现状是"人肉回归"：每次动 main.ts 都要手工点一遍全部交互。单人项目里，这类回归最容易被跳过，于是 bug 存活到用户（哪怕用户就是自己）撞上为止。

**建议的两步走（按投入产出排序）：**

- **第一步（便宜，先做）**：把可纯化的判定逻辑抽成纯函数搬进 `src/shared/`，直接进现有 vitest。候选：双击/单击判定器（输入两次 pointerdown 时间戳，输出 click/dblclick）、手势判定器（输入时间戳+累计路径，输出是否触发）、编辑提交状态机（输入事件序列，输出数据变更）。这些是纯时间/数值逻辑，零 DOM 依赖。
- **第二步（贵，看情况）**：引入 jsdom/happy-dom + @testing-library 做渲染层集成测试。对这种重手势的自定义 UI，DOM 测试的性价比一般，**不建议急上**——先让第一步的纯函数测试把状态机护住。

### 主进程 store.ts 也没有测试

`store.ts` 依赖 `electron` 的 `app.getPath`，测试需要 mock。它的逻辑（防抖、双写、读回退）恰好是健壮性篇讨论的重点，改原子写（P1-4 建议）时**必须有测试护航**，否则是把数据安全赌在没验证的重构上。建议随 P1-4 一起补一个 `tests/store.test.ts`（mock `electron` 模块，验证：防抖合并、主文件坏时回退备份、写入失败不抛穿）。

## 工程链路

| 环节 | 现状 | 评价与建议 |
| --- | --- | --- |
| 类型检查 | `npm run typecheck` 零错误，`env.d.ts` 给 `window.qink` 提供了类型 | ✅ IPC 桥两端都有类型约束，preload 改名会立刻编译报错——这个很多项目都没做 |
| Lint / 格式化 | 无 ESLint、无 Prettier | P3：单人项目纪律可以替代，但 `npm i -D eslint prettier` + 一次配置的成本约半小时，换来的是风格永久统一和低级错误（未用变量、可疑相等）自动拦截。建议加 |
| CI | 无（无 GitHub Actions 等） | P3：现在是纯本地开发。若仓库上了远端，加一个 `test + typecheck` 的双命令 workflow 是十行 YAML 的事。优先级低于加 lint |
| 打包 | electron-builder，NSIS 安装版 + 便携版双产物（`electron-builder.yml`） | ✅ 配置干净；国内网络镜像的注意事项已写进 AGENTS.md |
| 自动更新 | 无 | P3：v0.1.0 无装机分散时不急；以后用户多了，没有更新的安装版会变成"永远停在旧版"的存量包袱，届时上 electron-updater + GitHub Releases |
| 版本管理 | 数据 `version: 1` 已预留；**注意：当前工作区有约 +1392 行未提交改动**（悬浮球、手动调尺寸等已完成的里程碑） | 建议尽快提交——这批改动已经过 M 系列验收，长期游离在版本历史外不利于回溯 |

## 工程文化观察

`tasks/lessons.md`（自我纠错记录）+ `docs/adr/`（7 篇决策记录）+ `.scratch/<feature>/` 问题追踪的流程是真实在用的——ADR 里能查到"为什么放弃 Voronoi 改蛛网几何""为什么贴纸从不读 win.getBounds()"这类关键决策的来龙去脉。**对一个会被长期维护的个人项目，这套记录的价值会随时间复利**，建议保持。
