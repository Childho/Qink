# 数据安全与健壮性审查

> 结论：安全配置在 Electron 个人应用里属于上游水准（CSP、contextIsolation、零运行时依赖、零网络请求）；数据 resilience（抗灾）有真实事故驱动的双写备份设计。两个结构性缺口：**落盘非原子**（断电瞬间可能写坏文件）和 **IPC 数据不校验**（坏数据会被原样写进主文件和备份）。

## 安全配置逐项过堂

| 检查项 | 状态 | 证据与说明 |
| --- | --- | --- |
| CSP（内容安全策略） | ✅ 有 | `index.html:7`：`default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:`。默认拒绝一切外部加载。`style-src` 的 `unsafe-inline` 是必须的——JS 里大量直接设置 `el.style.xxx`，这类内联样式操作就需要它放行；不算放水 |
| contextIsolation（上下文隔离） | ✅ 开（默认值未被关闭） | `webPreferences` 里没有显式关它，Electron 38 默认开启。渲染层拿不到 Node 能力 |
| nodeIntegration | ✅ 关（默认） | 同上，未显式开启 |
| sandbox | ⚠️ `sandbox: false` | `index.ts:80`。这是 electron-vite 模板的默认值（preload 用 CJS 打包时的历史习惯）。**实际上这个项目的 preload 只 import 了 `contextBridge` 和 `ipcRenderer`（`preload/index.ts:1`），一个 Node API 都没用**——大概率可以直接改 `sandbox: true` 收紧，把渲染层进程关进 Chromium 沙箱。建议实测一次（electron-vite 5 打包兼容性验证），成了就是零成本的安全增强 |
| 远程内容 | ✅ 零 | 无任何 `loadURL` 到外部地址（dev 模式的 localhost 除外）、无网络请求代码、无远程图片 |
| 运行时依赖 | ✅ 零 | package.json 的 `dependencies` 为空——供应链攻击面（第三方库被投毒）为零 |
| shell 调用 | ✅ 白名单路径 | 唯一的 `shell.openPath` 打开固定目录（`index.ts:211`），无用户可控参数 |
| 窗口打开行为 | ⚠️ 未设防 | 没有 `webContents.setWindowOpenHandler(() => ({ action: 'deny' }))`。当前页面里没有任何链接，实际风险接近零；但作为纵深防御（万一未来引入富文本/链接），加一行是免费的保险 |
| 单实例锁 | ✅（有边注） | `index.ts:35`，二次启动唤起已有实例，避免两个实例写同一个 data.json 打架。**边注**（项目自己的教训，`tasks/todo.md`）：dev 版（app name `qink`）与正式版（`Qink`）的 userData 路径不同，**两者的单实例锁互不感知，可以同时运行**，而数据都写 `文档\Qink\data.json`，后写者覆盖先写者——开发期验证数据时必须先确认只有一个实例在跑。这是开发流程风险而非用户风险，记录在案 |

**总体判断**：渲染层即使被注入脚本（目前不存在这个入口），它能做的也只有：改内存数据 → 发 IPC 落盘、拖窗口、退出程序。破坏面被 preload 的窄接口天然限制住了。这是"接口收窄"带来的结构性安全，比堆防御代码更可靠。

## 数据落盘机制

现状设计（`store.ts`）：

- **双写**：主文件 `文档\Qink\data.json` + 备份 `AppData\...\data-backup.json`，每次落盘先后都写（`store.ts:58-73`）；
- **防抖 300ms**：打字、拖动这类高频操作合并成一次写盘（`store.ts:51`）；
- **启动自愈**：启动即 `queueSave()` 一次，主文件被清理工具误删时立刻重建（`index.ts:43`）；
- **读回退**：主文件读不出来（损坏/删除）时自动回退读备份（`store.ts:27-35`）；
- **备份的由来是真实事故**：`store.ts:10` 注释记录"文档目录曾观察到被外部整体删除（安全软件/清理工具）"——这是吃过亏换来的设计，比任何理论分析都有说服力。

### P1-4 写入非原子：断电瞬间的截断风险

`persist()` 直接 `writeFile(dataFile(), json)`（`store.ts:62`）。文件写入不是原子的——**断电/蓝盘/进程被杀发生在写入中途时，data.json 会留下半截 JSON**（比如只有前 3KB）。下次启动时主文件解析失败 → 回退备份（上一轮成功写入的内容），用户损失的是主文件里比备份"新"的那部分（两者通常相差无几，因为每次 persist 都双写）。

**辩证地看**：双写备份已经把最坏情况压到"丢最近 300ms~几秒的改动"，这是可用的兜底。但它有两个软肋：
1. 若断电恰好发生在**备份**写入中途（备份排在主文件之后写），则主文件半截 + 备份半截，**两个都坏**，全量丢失；
2. 半截文件会一直留到下次启动才被发现，期间用户如果以为数据在持续保存，会继续往内存里堆新数据——不，重启后其实就读备份了，损失封顶在断电时刻。真正的问题是场景 1。

**建议（改动约 10 行）**：写临时文件 + 原子改名替换——

```
写 data.json.tmp → rename 成 data.json（Windows 上 rename 是原子操作）
```

两个文件都这么处理后，任何时刻磁盘上要么是完整旧文件、要么是完整新文件，"半截"状态在结构上不可能存在。这是数据库 SQLite 等所有严肃存储的标配做法，值得引入。

### P2-5 IPC 数据不校验形状

`qink:data:set`（`index.ts:175`）把渲染层发来的对象直接 `setData` 落盘。现在渲染层是自家代码、没有外部输入注入点，所以**当前风险低**；但考虑两个未来场景：

- 渲染层某处 bug 造出畸形数据（比如 `tasks` 意外变成 `undefined`），会被**原样写进主文件和备份**，两处同时污染，回退机制失效；
- 第二阶段计划做 MCP（AGENTS.md 提到），外部工具一旦能写数据，校验就是必需品。

**建议**：在 `setData` 里做最小 schema 校验——顶层四键（goals/tasks/archive/settings）类型断言 + tasks 数组元素的 id/text/createdAt 字段检查，不合格拒绝并打日志。约 20 行，把"信任边界"从"整个渲染层"缩到"一个函数"。

### 数据兼容性现状

`loadData` 的 `{ ...defaultData(), ...JSON.parse(raw) }`（`store.ts:30`）是**浅合并**：文件里缺 `settings` 键时用默认补上（好）；但若 `settings` 存在而缺新字段（如老数据无 `noteMode`），合并后该字段是 `undefined`——好在消费端全部做了容错（`main.ts:1080` 的三元判断、`index.ts:64` 同）。`version: 1` 字段已预留但无迁移逻辑，当前只有一版，合理。**注意点**：`settings.autostart` 若老数据缺失会是 `undefined`，`setLoginItemSettings({ openAtLogin: undefined })`（`index.ts:45`）行为等于不开机自启——与默认值 `true` 相悖。属于理论边角（只有"手改过 JSON 且删了 autostart 键"才会触发），记录备查。

## 健壮性场景推演

| 场景 | 现状行为 | 评价 |
| --- | --- | --- |
| 数据文件被清理工具删除 | 启动时读不到 → 从默认开始；启动即 queueSave 重建空文件 | ✅ 自愈 |
| 主文件 JSON 损坏（半截） | 解析抛错 → 静默回退备份，用户无感知 | ✅ 可用（但见 P1-4，应让损坏不可能发生） |
| 磁盘满/权限拒绝，持续写失败 | 主进程控制台 `console.error`（`store.ts:65`），**用户完全看不到**，以为一直在保存 | ⚠️ P2-6：建议连续失败 3 次在贴纸角落显示一个小红点 + tooltip"保存失败"，最小成本堵住"静默丢数据"的信任漏洞 |
| 显示器拔掉后启动 | 位置钳制回主显示器工作区（`index.ts:139`） | ✅ |
| 跨午夜挂机 | 30 秒对表翻篇（`main.ts:818`），滚入/目标失效即时重算 | ✅ |
| 时钟回拨/时区变化 | 全部基于本地自然日推导，无 UTC 假设 | ✅（中国无夏令时，`daysSince` 的 Math.round 也对边界稳健） |
| 用户手改 data.json 塞了非法值 | 浅合并后进内存，渲染层可能渲染出怪东西 | ⚠️ 同 P2-5，schema 校验可一并堵住 |
