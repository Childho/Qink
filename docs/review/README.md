# Qink 项目全面审查（2026-09-11）

> 审查对象：当前工作区代码（含未提交的悬浮球/手动调尺寸改动，共 17 个文件、约 +1392/-408 行）。
> 审查方式：通读全部源码（src/ 约 3500 行）+ 配置 + 文档；运行 `npm test`（34 个测试全过）与 `npm run typecheck`（零错误）；实测运行中进程内存。
> 视角：使用体验、性能、代码质量、数据安全、测试与工程化五个维度。每条发现都附代码位置和证据，同时给出优点与软肋（辩证），建议按优先级排序。

## 一句话结论

**这是一个质量明显高于典型个人项目的代码库**：纯逻辑下沉到 `src/shared` 并有 34 个单测护住、注释解释"为什么"而不是"是什么"、有 CSP 安全策略、数据防抖落盘 + 双写备份、照顾了 reduced-motion（系统级"减少动画"设置）和键盘可达性。**主要短板不在"写错了什么"，而集中在三类**：① 少数交互边角场景（详见 UX 篇的竞态死区、误删无撤销）；② 数据落盘的极端断电风险（非原子写入）；③ 渲染层 1088 行交互逻辑没有自动化测试，每次改动全靠人肉回归。

| P3 | 无 ESLint / CI / 自动更新 | 项目根 | 单人阶段可接受，装机量上来后补 |

## 建议的处理顺序

1. **先修 P1 的两个交互问题**（删除撤销 + 双击竞态）——用户每天都会碰到的路径，改动小、收益直接。
2. **落盘改原子写**（写临时文件再改名替换）——十行以内的改动，把断电风险从"靠备份兜底"变成"结构上不可能坏"。
3. **给悬浮球加一次性的"如何找回"引导**（首启气泡或 README 截图）——成本最低的 P1。
4. P2 的渲染层测试：把双击判定、手势路径累积、排序预览这些"可纯化"的逻辑抽进 `src/shared`，补 vitest。这是长期收益最大的一项，但工作量也最大，不急于一时。
