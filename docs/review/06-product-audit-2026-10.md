# Qink 产品×工程全面审查（2026-10-09）

> 审查对象：HEAD `5391b0b`（开源后最新提交）。基线：`npm test` 52/52 通过、typecheck 零错误。
> 审查方式：四路并行深读（主进程与数据层 / 渲染层交互与动效 / shared 逻辑与测试 / 历史审查闭环）+ 关键证据逐一人工复核 + **真实使用数据取证**（唯一真实用户＝作者本人，2026-09-11 起一个月）+ 运行态观测（安装版 4 进程合计 ≈302MB，tasklist 实测）。未启动 dev 实例——既有教训：dev 与正式版双写同一 `data.json`。
> 本轮与 2026-09-11 五篇审查的关系：不重复其结论，重点核查其闭环情况（结论：P1×4 零修复）并向上找结构性原因。

---

## 1. 一句话判断

**工程质量和克制度在同类个人项目里处于上游，但「让最重要的事天天被看见」这一核心承诺，在唯一真实用户的桌面上正在落空：三个核心目标此刻全部是引导文字；与此同时 9/11 审查的 4 个 P1 一个月后零修复、「毛玻璃」产品身份在开源大提交中被静默删除——产品有从「目标被看见的工具」漂向「动画精致的桌面玩具」的惯性。**

---

## 2. 已经做对的事情

1. **周期目标「推导式失效、存储层永不清空」**（`src/shared/dates.ts:6,109-112`）：目标是否有效由周期键实时比对，写操作永不删数据，系统时钟错乱也不会误删。这是「翻篇」的正确地基，不要改。
2. **今日任务的轻量纪律守住了**：一行输入回车即加，截止时间/标记/排序全部是可选属性，due 窄语法宁可拒绝也不静默存错（`src/shared/due.ts:63-68` 注释原话「静默存错是信任杀手」）。别因为「别的软件都有」而加标签、优先级。
3. **碎裂动画 vs 效率的张力解得很好**：27 片恒定成本、只锁被完成的那一行（`main.ts:919-921`）、连续完成可并行、`prefers-reduced-motion` 全链路覆盖、隐藏窗口 900ms 兜底。第 1 次惊艳、第 100 次不烦，靠的就是不阻塞＋时长克制——不要加长动画，也不需要频率衰减。
4. **常驻成本纪律**：渲染层仅一个 30s 幂等 tick（`main.ts:1155-1164`），主进程零常驻定时器，拖动 16ms 节流。空闲 CPU≈0，常驻开销控制是全项目最好的方面之一。
5. **几何单源 + 主进程权威记账**：全部尺寸从 `shared/window.ts` 推导，主进程绝不读 `getBounds()`（透明窗口 HWND 外扩的真实教训，`src/main/index.ts:27-30`）。这套「注释保存踩坑史」的做法值得保持。
6. **shared 纯函数层 + 单测钉住宪法级规则**：周期键跨年（2026-W53）、滚入午夜边界、due 判定表全分支、四分区幂等不变量。52 个测试里最有价值的正是这些。
7. **本地优先边界**（无账号/无云/无遥测/明文 JSON 用户可直接打开）是承诺也是差异化，守住。
8. **lessons.md 的自我纠错密度罕见**，且确实被后续复用（图标三层排查直接引用既有脚本）。

## 3. 核心问题

### P0-1 核心目标在真实桌面上长期为空（产品命门）

- **现象**：季/月目标在当前数据谱系（9/11 文件被删后重建）里从未写过；周目标停在 `2026-W40`，而今天已是 `2026-W41`——三个目标位此刻全部显示引导文字。
- **证据**：`Documents\Qink\data.json` → `goals: {quarter: null, month: null, week: {periodKey: "2026-W40", text: "竞标资料与交接"}}`；`weekKey(2026-10-09) = 2026-W41`（已用 shared 同算法复核）。
- **为什么是问题**：产品存在的唯一理由是「最重要的事天天被看见」。当前被天天看见的是三行占位提示。10/1 恰逢月+季双边界，一个长假过去目标区自然清零，而产品没有任何「上周期目标是什么」的提示帮用户低成本重启——重写成本完全落在用户身上。
- **影响**：核心价值空转；引导文字天天看也会脱敏，最终用户对目标区视而不见。
- **严重程度**：**P0**（价值归零级，虽非崩溃级）。

### P0-2 双重损坏 = 静默清零并立即销毁现场

- **现象**：主文件与备份都不可读时，落入 `defaultData()`，且启动即 `queueSave()` 把空数据覆盖写回两个文件。
- **证据**：`src/main/store.ts:26-38`（恢复链全在 catch 里静默）+ `src/main/index.ts:40-43`（启动自愈落盘）。没有损坏提示、没有把坏文件改名留档（如 `data.json.corrupt`）、没有第三副本。
- **为什么是问题**：产品承诺「本地数据、无云端」，本地可靠性就是产品能力本身。主备同坏（同一磁盘故障/同一种清理工具扫两个目录）时，全年目标与 49 条归档无声蒸发，且现场被覆盖后无法事后抢救。
- **影响**：一次异常可能丢掉全部数据——这是全项目唯一「存在级」风险。
- **严重程度**：**P0**。

### P1-1 落盘非原子 + 退出不 flush（通往 P0-2 的传送门）

- **证据**：`store.ts:58-62` 直接 `writeFile` 覆写，无「临时文件+rename」；`before-quit` 只设标志（`index.ts:50-52`），300ms 防抖窗口内的最后修改随退出丢失；断电半写的截断文件正是触发 P0-2 恢复链的常见入口。9/11 审查已建议「十行改完」，一个月未做。
- **严重程度**：**P1**。

### P1-2 删除任务零确认零撤销

- **证据**：`main.ts:900-917` 一次误点右键「删除」即永久丢文本（380ms 收拢动画只是演出，不是反悔窗口）；归档只收「完成」不收「删除」；「删除」与「改写」在菜单里相邻。9/11 P1 未修。
- **严重程度**：**P1**（信任级，高频路径）。

### P1-3 「毛玻璃」名存实亡，对外叙事失实

- **证据**：`src/` 全仓 grep `wallpaper|backdrop|mist|acrylic` 零命中；材质是实色 `#fafaf8`「蛋白石琉璃」（`style.css:16-18`）；壁纸采样系统（M5/M12/M14 三个里程碑的心血）在开源提交 `a3ffa6f` 中整体删除，无对应 ADR；而 `README.md:3,9`、`package.json:4`、`CONTEXT.md`（「半透明」）仍宣称毛玻璃，ADR-0003/0004/0007 未标废弃。
- **为什么是问题**：「实色琉璃」本身是合格取舍（可读性与壁纸彻底解耦、零 blur 依赖全平台一致），**问题在叙事没跟上决策**：开源仓库的门面描述与实物不符，贡献者按毛玻璃预期来会落空，决策无记录意味着目标漂移没有被文档捕获。
- **严重程度**：**P1**（产品身份与开源诚实）。

### P1-4 隐藏交互 × 自动收起的复合风险

- **证据**：双击球是展开的唯一显式路径，单击球零反馈（9/11 的 P2 建议「单击轻弹跳+提示」未做，仅靠 hover title `index.html:34`）；10 分钟空闲收起（`main.ts:49`）让「变球」成为高频事件；双击边缘重置尺寸同样无提示（`main.ts:1436`）。已完成清单与标记置顶有右键菜单入口（`main.ts:1009`），不算盲区。
- **为什么是问题**：新手会反复经历「贴纸变球 → 单击没反应 → 以为坏了」。收起越自动，展开的可发现性越重要。
- **严重程度**：**P1**。

### P1-5 滚入任务无上限、无老化、无出口

- **证据**：`isRolledIn` 是纯布尔「创建日≠今天」（`dates.ts:103-106`），拖 1 天与拖 90 天同色同权重；`daysSince` 有测试却无任何 UI 出口；逾期任务从次日起永久霸占红色置顶区，只能完成/改期/删除才解除。真实数据：7 条未完成任务中 **6 条是滚入旧任务**（实体店对账sop、电商售后sop 等，多来自上周）。
- **为什么是问题**：「跨日滚入保持连续性」正在滑向「清不掉的任务垃圾场」；红色永久置顶制造慢性焦虑并最终脱敏（spec 自己也承认「多条逾期全红可能脱敏」）。
- **严重程度**：**P1**（机制级；半年后「列表顶端持续膨胀」的预言已在微型 scale 上应验）。

### P2（简列）

- 多显示器：所有几何调用点一律 `getPrimaryDisplay().workArea`（`index.ts:146,189,240,267`），副屏被强制吸回主屏且坐标被覆写；运行时无 `display-removed/metrics-changed` 监听。属 spec 取舍，但代码与 README 都没向用户声明「只在主屏活动」。
- 渲染层（架构上的状态源，`store.ts:44` 注释自认）零自动化测试；`main.ts` 1088→**1655 行**、模块级 `let` 15→**23 个**，「下次大改时拆分」的时机已出现两次（M15、丝滑还原）均未执行。
- `store.ts` 零测试；`version: 1` 字段无任何消费（升级/降级裸奔）；`setData` 不校验形状。
- 归档体验两处：打开后约 0.7–1.1s 行不可点（`archive.ts:288,366-374`）；列表溢出时滚轮翻日失效，需无提示的 Alt+滚轮（`archive.ts:68`），而「今天」几乎总是溢出的。
- 保存失败零感知：主文件失败仅 `console.error`（打包后无人可见），备份失败完全静默（`store.ts:63-72`）。
- dev/正式/便携版共享同一 `data.json`，单实例锁却按 userData 隔离 → 双开互覆（`store.ts:8` vs `index.ts:34`）。

## 4. 产品矛盾

| # | 张力 | 当前裁决 |
|---|------|---------|
| A | 「目标要天天被看见」 vs 「10 分钟自动收起」 | **未解好，且与 P0-1 互为放大器**：目标区若是引导文字，收起就毫无成本——用户已用脚投票（真实数据 `noteMode: "ball"`）。裂缝常亮+速记胶囊缓解了一半，但「被看见」的主体（目标）空了，收起就更无所谓。 |
| B | 「今日任务足够轻」 vs 「截止/标记/排序/历史逐渐增加」 | **暂时守住**：属性全可选、输入行仍是一行。但 260ms 单击延迟（单击改写与双击标记并存的固有税）与红/紫/橙三色阶已在认知边缘，下一个「锦上添花」属性可能压垮它。 |
| C | 「常驻桌面」 vs 「Electron 常驻成本」 | **接受即可**：实测 4 进程 ≈302MB。对「桌面物件」偏重，但换来动画能力与开发效率；不值得为此迁移技术栈，也不值得做亚百毫秒优化。 |
| D | 「完成仪式感」 vs 「高频操作效率」 | **解决得最好的一对**（见「做对的事」第 3 条），是其他张力的正面样板。 |
| E | 「本地简单可靠」 vs 「单 JSON 损坏风险」 | **当前输得最彻底的一对**（P0-2 + P1-1）。「简单」不能以「一次异常全丢」为代价，否则承诺本身变成风险。 |

## 5. 下一轮迭代（按价值排序，6 项）

### ① 数据耐久三件套：原子写 + 坏档保护 + 退出 flush

- 当前状态：`store.ts` 73 行，非原子写、双坏静默清零、退出丢最后 300ms。
- 问题：P0-2 + P1-1，产品唯一的「存在级」风险。
- 为什么值得现在做：改动局部（单文件+退出钩子）、无产品争议、可直接补 `store.test.ts` 填上测试空白；9/11 就该做。
- 用户感知：「再也不会因为一次异常丢掉所有记录」——平时无感，出事时是全部。

### ② 目标翻篇的善后：新周期不冷启动

- 当前状态：周期更替=目标无声消失，界面只剩引导文字；季/月从未被写过、周目标断在 W40。
- 问题：P0-1 的机制根源——翻篇对用户是一堵墙，产品没给梯子。
- 为什么值得现在做：核心价值空转中；真实数据已给出证据；方案便宜（展示引导文字时附带一行淡字「上季是：X」，点击可沿用/改写）。
- 用户感知：每周一早上打开便利贴，上周的目标还在视线里，改两个字就是新目标，而不是从「______」开始回忆。

### ③ 删除可撤销

- 当前状态：右键删除即永久消失，恢复只能手改 JSON。
- 问题：P1-2，高频菜单的相邻项，误触即数据丢失。
- 为什么值得现在做：改动小（5 秒撤销提示，或删除入归档带标记）；这是 9/11 两个交互 P1 中更容易的一个。
- 用户感知：误点不再心悸。

### ④ 悬浮球单击反馈 + 首启一次性提示

- 当前状态：单击球零反应，展开全靠「猜到双击」；双击边缘重置、手势等隐藏交互无任何常驻暗示。
- 问题：P1-4，与 10 分钟自动收起复合成「贴纸失踪」体验；顺带可关闭 9/11 的托盘可发现性 P1。
- 为什么值得现在做：自动收起让这个问题的暴露频率上升了一个量级。
- 用户感知：第一次收起后就知道怎么回来；「这软件是不是坏了」的疑问消失。

### ⑤ 滚入任务的老化与出口

- 当前状态：滚入纯布尔、逾期永久红顶、`daysSince` 有测试无 UI。
- 问题：P1-5，「任务垃圾场」在真实数据里已现雏形（6/7）。
- 为什么值得现在做：机制问题随时间复利，越晚做存量越大；最小方案（行尾淡字「第 3 天」＋右键「收进归档」）不引入新概念。
- 用户感知：列表顶端不再无限膨胀；拖延天数可见本身就是温和的推力。

### ⑥ 材质叙事对齐：改口 + 补 ADR

- 当前状态：README/package.json/CONTEXT 仍说毛玻璃，实为实色琉璃；三篇玻璃 ADR 未标废弃。
- 问题：P1-3，开源门面失实。
- 为什么值得现在做：纯文档工作，半小时；避免下一个贡献者按毛玻璃预期贡献代码。
- 用户感知：仓库描述即所得；「为什么不是毛玻璃」有正式答案。

## 6. 不建议做

- **云同步 / 账号 / 标签 / 项目 / 优先级矩阵 / AI 助手**：没有一项服务「被看见」，每一项都把便利贴变成软件。
- **目标完成率统计、趋势图**：直接违背 ADR-0002 的不对称策略——会把「看见」变成「管理」，把便利贴变成 KPI 面板。
- **通知 / 弹窗 / 闹钟**：「提醒靠看见」是产品哲学，逾期裂缝已经是这门语言的全部；加通知就跨过了「不打扰」的边界。
- **为恢复毛玻璃重回实时玻璃 API**（Win11 backgroundMaterial / 私有 API）：Win10 无稳定方案，M11 两次实测失败已证明。除非作者判定「通透感」是身份底线——那也应作为独立立项论证，而非顺手改。
- **引入前端框架、立即大拆 main.ts**：复杂度尚未产生真实代价；下次触碰交互时顺手抽取纯函数即可（due.ts 已是样板）。
- **多便签 / 全局快捷键 / 设置页面**：每一样都在稀释「一张便利贴=整个产品」。
- **亚百毫秒级性能优化**：常驻成本已优，302MB 是 Electron 的地板价，优化它不如接受它。

## 7. 最终裁决

> 如果 Qink 现在只能进行一轮开发，最应该解决什么？

**数据耐久三件套（迭代①）。**

理由：这是存在性问题，其余是价值问题。Qink 对用户的隐性契约是「数据在你自己手里，所以丢不得」——当主备双坏会静默清零并销毁现场时，这条契约是空的；而触发它的入口（非原子写+断电）每天都敞开着。修复它不需要任何产品决策、改动局限在一个 73 行的文件、还能顺势补上数据层零测试的空白——是全部候选里「确定性×代价」比最高的一项。

目标翻篇善后（迭代②）是紧随其后的第二轮：它是产品命门，但「上周期目标怎么呈现、要不要入归档」需要作者本人做设计决策，不应由一轮开发自行拍板。建议带着本报告 P0-1 的真实数据证据（W40 空窗、季/月从未使用）先做一次方案拷问再动手。
