# 代码质量与架构审查

> 结论：架构分层正确、注释质量罕见地高、命名与概念和领域文档（CONTEXT.md）严格对齐。唯一的结构性痛点是渲染层 `main.ts` 1088 行单文件承载了六套交互状态机，已经到了"改一处需通读全文件"的临界点。

## 架构分层

```
src/shared/   纯逻辑：日期周期、任务排序、窗口几何、（shatter 的几何部分）
src/main/     窗口/托盘/IPC/落盘——所有需要操作系统权限的事
src/preload/  IPC 桥——渲染层唯一的后门，面很窄（13 个方法）
src/renderer/ UI 编排 + 动画
```

**做对了的：**

- **"渲染层是状态源，主进程是落盘器"**（`store.ts:44` 注释）——职责单向：渲染层改内存 → 全量发给主进程 → 防抖落盘。单窗口小数据场景下这是最简单的正确架构，没有过度设计成双向同步/数据库。
- **可测逻辑全部下沉 shared**：周期键推导（ISO 8601 周算法，`dates.ts:67`）、三层分区排序（`tasks.ts:8`）、窗口钳制几何（`window.ts`）、碎裂几何裁切（`shatter.ts` 的 Sutherland–Hodgman / Liang–Barsky）。这四块正是"错了会静默污染数据"的高危区，全部有单测（测试篇详述）。
- **preload 暴露面窄且只读语义清晰**：能触发的副作用全部白名单化（拖动/退出/自启/开文件夹），没有暴露任何通用的 IPC 通道。
- **IPC 入口有输入校验**：`qink:note-resize` 对宽高做了 `Number.isFinite` 检查（`index.ts:185`），`qink:form-change` 白名单校验 mode 值（`index.ts:252`）。

**一个设计上的亮点**：主进程不信任 `win.getBounds()`，自己记账 `noteSize`（`index.ts:28-31` 的注释完整记录了为什么——Windows 会给透明窗口的 HWND 自动外扩，读矩形会把假尺寸当真导致位置越界 bug）。这种"把踩过的坑写成决策记录"的注释是这个代码库最值钱的资产。

## 注释质量

值得专门表扬。抽查几例：

- `index.ts:28-30`：记录 bug 根因（M14 修复），后人不会再犯；
- `main.ts:77-81`：解释自适应高度上报的死锁风险（"若只报可见高，窗口永远不会长"）——这是不改代码就会重新引入的隐性约束；
- `archive.ts:325-327`：解释三阶段批量读写为什么必要（布局抖动）；
- `style.css:202-203`：解释 transition 为什么显式列属性。

这些注释的共同点是**讲约束和为什么，不复述代码**。对单人长期维护的项目，这比测试还重要。

## 结构性问题

### P2-1 渲染层 main.ts 1088 行，六套状态机同居一文件

粗略拆分一下这 1088 行承载的东西：

1. 数据引导与渲染（boot/render/renderGoals/renderTasks）
2. 行内编辑状态机（startGoalEdit/startTaskEdit，各带 finished 标志防重入）
3. 拖动排序状态机（taskDrag 快照/让位/落位，约 120 行）
4. 窗口拖动（wireDrag，锚点 + rAF）
5. 边缘调尺寸（wireResize，双击重置）
6. 悬浮球交互（wireBall，长按/双击/速记）
7. 右键手势（长按晃动开归档）+ 全局键盘路由

它们通过约 15 个模块级 `let` 变量耦合（`composerOpen`、`suppressClick`、`taskDrag`、`editTimer`、`landingTimer`、`gestureFiredAt`……）。目前没出事，是因为作者对全局状态有清晰的纪律（每个变量的注释都到位）。**但每加一个交互，人脑要追踪的隐式交互就多一份**——比如 `renderTasks` 开头那句 `if (archive?.isOpen() || taskDrag) return`（`main.ts:248`）就是在同时守护两个状态机的边界。

**建议**（不急于一时，下次大改交互时顺势做）：按上面 1–7 拆成 `renderer/src/` 下的模块文件，每个状态机的 `let` 收进自己的闭包或小对象。主文件回到 200 行以内的"装配层"。

### P2-2 suppressClick 的全局点击吞咽是脆点

拖动排序/窗口拖动结束后用 `suppressClick = true` + `setTimeout(0)` + document 捕获阶段拦截下一次点击（`main.ts:541-544,732-737,879-881`）——防止"松手那次 click 被当成任务点击"。三处复制粘贴同一模式。它能工作，但依赖"click 一定在 setTimeout(0) 之前到达"这个时序假设。**更稳的写法**是在 pointerup 的同一事件序列里用 `event.preventDefault()` 或记录 pointerdown 起点（移动超阈值即视为拖动、忽略后续 click），把"吞点击"变成显式判定而非时序赌注。目前不构成 bug，列为重构时的顺手项。

### 小项

- **CSS 出现"第二段落"**：`style.css:518` 起是一批无注释的单行规则（`.goals { flex: 0 1 auto; ... }` 等），与前文分区注释风格脱节，像是后期快速追加。建议按现有分区归并，给每段补上"为什么"。
- **魔数 11px**：归档恢复动画里行间距用 `-11px` 硬编码（`archive.ts:308`），与 `.archive { gap: 11px }`（`style.css:386`）隐性耦合，改 CSS 间距会静默破坏收拢动画。至少该在两处互相引用，或用 CSS 变量同源。
- **死代码检查**：未发现。`shatter.ts` 导出的 `GlassCells`/`CrackPattern`/`clipSeg` 均有消费方；`style.css.d.ts` 是给 CSS import 的类型声明（TS 需要），不是垃圾。
- **命名与领域语言一致**：代码里的"滚入/翻篇/修复/贴纸/悬浮球"与 CONTEXT.md 术语表一一对应——读代码不需要翻译，这一点很多商业项目都做不到。

## 复杂度抽查（易错算法验算）

- **ISO 周键**（`dates.ts:67`）：周四定年 + 首周四定基准，实现正确，测试覆盖跨年边界（2026-12-28 等）。
- **Sutherland–Hodgman 多边形裁剪**（`shatter.ts:29`）：四边界顺序裁剪、退化输出判空，正确；碎片并集覆盖性由最外环半径罩住整行保证（`shatter.ts:106-107` 有注释）。
- **applyReorder 分区钳制**（`tasks.ts:25`）：zone 计算与 UI 层让位预览（`main.ts:472-482`）语义一致——但注意这是**两处实现**（UI 层数 classList，数据层数数据字段），一致性目前靠人肉对齐，见测试篇建议。

## 代码质量篇结论

| 优先级 | 建议 |
| --- | --- |
| P2 | 下次大改交互时把 main.ts 按六套状态机拆模块，模块级状态变量各归各位 |
| P3 | suppressClick 三处复制粘贴收敛成一个工具函数（或改为显式拖动判定） |
| P3 | style.css 后半段归并分区 + 补注释；11px 魔数与 gap 同源 |
