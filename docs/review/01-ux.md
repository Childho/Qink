# 使用体验审查

> 术语约定：「贴纸」= 主界面那张便利贴；「悬浮球」= 收起后的小圆球；「归档/已完成清单」= 翻阅历史完成任务的视图。所有行号基于 2026-09-11 的工作区代码。

## 总评

交互设计的完成度很高，而且能看出明确的取舍意识——很多地方代码注释直接写明了"代价是什么"（例如单击改写有 260ms 延迟感，`main.ts:349`）。核心招牌"碎裂完成 → 碎片拼回带永久裂纹"的叙事链完整，细节反馈（输入落定扫光、草稿保留、IME 保护）超出个人项目的平均水准。问题集中在少数边角场景和"出错后的退路"上。

## 做得好的地方（值得保持）

**1. 完成任务的碎裂叙事完整且有情感设计。**
点圆圈 → 行碎成放射状碎片飞散（`shatter.ts:207`）→ 在已完成清单里这些碎片又"拼回来"，并且带着永久发丝裂纹（`archive.ts:181` 的 assembleRow + `crackLines`）。碎过又拼回的行真的不一样——这是产品的灵魂，实现质量对得起这个创意。

**2. 输入反馈细节到位。**
进入编辑时下边框从左生长（`style.css:325` 的 `.input-active`），保存瞬间再扫实一遍（`.input-flash`）。保存这个动作本来是无形的，现在有了可感知的确认，这是很成熟的微交互思路。

**3. 草稿不丢。**
新增任务的输入行失焦关闭后，草稿被记住，提示行变成"继续写下刚才的事…"（`main.ts:313`）。用户点了别处再回来，字还在。

**4. 中文输入法保护（对中文用户至关重要）。**
所有键盘监听都先判 `e.isComposing || e.keyCode === 229`（`main.ts:229,264,599,1050`）——用拼音输入法打字时按回车选词，不会被误当成"确认保存"。很多国产小工具栽在这，Qink 全都防住了。

**5. 无障碍与键盘可达性超出预期。**
- 尊重系统"减少动画"设置：碎裂直接跳过（`main.ts:636`）、全局动画时长归零（`style.css:539`）。
- 键盘全通：目标行/提示行可 Tab 聚焦回车激活、菜单支持方向键导航、归档支持 ←/→ 翻日、Ctrl+Shift+H 开关归档（`main.ts:750`）。
- focus-visible 焦点圈（琥珀色）在所有可点元素上统一（`style.css:527`）。

**6. 拖动手感的技术选型正确。**
自绘拖动用"按下时锚点 + 绝对位移"定位窗口（`main.ts:831-871`），不累加增量，从结构上杜绝丢帧漂移；位移按 rAF（浏览器的"每帧一次"机制）合帧上报。窗口拖动期间的坐标回传做了 16ms 节流（`index.ts:125`）。

**7. "弄丢贴纸"的退路设计。**
关闭 = 隐藏进托盘不退出（`index.ts:92`）、再次双击启动文件会唤起已有实例（单实例锁，`index.ts:35`）、位置恢复时钳制回主显示器工作区防止丢在已拔掉的屏幕外（`index.ts:139`）。启动时立即落盘一次，数据文件被误删也能自愈重建（`index.ts:43`）。

**8. 拖动排序的分区钳制语义一致。**
预览落点钳制在同分区内（`main.ts:476`），落手写回数组的 `applyReorder`（`shared/tasks.ts:25`）用同一套分区逻辑——所见即所得，不会出现"拖到顶却被滚入区挡住"的困惑。两边逻辑分别在 UI 层和数据层实现，靠单测保数据层，靠人工保 UI 层（这是测试篇要谈的缺口）。

## 问题清单

### P1-1 删除任务无撤销、无确认 —— 出错后没有退路

`main.ts:610` `deleteTask` 直接把任务从数组里过滤掉然后落盘。对比一下两条终结路径：

- **完成**：碎裂 → 进归档 → 还能"修复"回今天（`main.ts:719` onRestore）。
- **删除**：直接消失，什么都不留。

右键菜单里"删除"和"改写"相邻（`main.ts:371`），误点概率不低。任务文字是用户亲手写的目标，误删一条昨日滚入的任务，既不在归档也无法找回。

**辩证**：加"撤销"要引入撤销栈或最近删除区，与产品的极简哲学（CONTEXT.md 里明确 Avoid 回收站）有张力。**最小可行方案**：删除时任务先进归档但带一个"已删除"标记，或在菜单点击后给 3–5 秒的行内"已删除 · 撤销"提示条。前者改动最小——本质是把"删除"降级为"完成且不计入"，数据永远可追回。

### P1-2 单击改写与双击标记的竞态死区（260–500ms）

任务文字的交互共用一个点击序列（`main.ts:349` 注释自己也承认这个代价）：单击 260ms 后触发改写（`EDIT_DELAY_MS = 260`，`main.ts:383`），双击触发标记置顶。问题是 **Windows 判定"双击"的默认时间窗是 500ms**——两次点击间隔落在 260–500ms 之间时：

1. 第一次点击后 260ms，改写定时器先触发，文字被替换成输入框；
2. 第二次点击落在输入框上，原文字元素已不在，dblclick 不会在原目标上合成；
3. 结果：用户想标记置顶，得到的是编辑模式，原意丢失。

双击快的人（<260ms 间隔）一切正常，所以开发者日常测试发现不了；慢一点的双击用户会稳定踩中。这是当前交互里最实际的缺陷。

**建议**：把 `EDIT_DELAY_MS` 提到 450ms 左右（贴近系统双击窗，死区收窄到几乎不存在），或改为自己在 pointerdown 时间戳上判定双击（不依赖系统 dblclick 事件），单击延迟就能同时降下来。**辩证**：延迟加大意味着单击改写的"跟手感"变差——但"点错了变编辑"远比"慢半拍才编辑"更伤信任，两害相权取其轻。

### P1-3 悬浮球/托盘的可发现性 —— Win11 用户可能"弄丢"应用

贴纸 `skipTaskbar: true` 不进任务栏（`index.ts:75`），唯一常驻入口是托盘图标（`index.ts:148`）。但 **Windows 11 默认把新出现的托盘图标折叠进"隐藏图标"溢出抽屉**，需要用户手动把它拖到常驻区。后果：用户收起成悬浮球 → 悬浮球在某次重启后……不，悬浮球不会消失；真正的场景是用户点了右上角 ×（= 隐藏）或重启后贴纸没显示（位置在屏幕外被钳回、但用户忘了它在哪），又在任务栏里找不到 Qink，以为程序没了。

**辩证**：这不算代码 bug（行为都是对的），是 Electron 托盘应用的通病。**最小成本方案**：首次运行时弹一次气泡通知（tray.displayBalloon）告知"Qink 常驻在此托盘"；或在 README 放一张托盘位置截图。代码侧还可以考虑在"显示贴纸"时让窗口闪一下焦点。

### P2-1 Escape 收起贴纸可能超出用户预期

贴纸空闲态按 Escape 会整个收起成悬浮球（`main.ts:749`）。设计意图是"一层层退出"，但用户在输入框按 Esc 关输入、在菜单按 Esc 关菜单后，再习惯性按一次 Esc 想"取消聚焦"，整个贴纸没了。虽然双击球能展开、无数据损失，但第一次发生时会有"我东西呢"的惊吓。**建议**：观察实际使用反馈再定；若改，可以要求连续两次 Esc 才收起。

### P2-2 球形态下的功能入口深

球形态下右键球体能出完整菜单（`main.ts:767` 的判定包含 `#dock`），这点做得对。但"展开贴纸"本身只有双击一条路（`main.ts:1044`），且单击球体无任何响应（长按是拖动、260ms 前移动会取消）。新用户第一次见到这个球，最本能的操作就是单击——没有任何反馈。**建议**：单击给个轻反馈（球轻微弹跳 + tooltip 提示"双击展开"），不改变功能。

### P2-3 其他小项

- **字号档位偏小**：小/中/大 = 12/13/15px（`style.css:26-28`）。13px 中文长时间阅读偏吃力，"大"其实也不大。可考虑 13/14/16 起步。属口味问题。
- **归档翻日有 280ms 节流**（`archive.ts:73`）：快速连续滚轮会被吞掉一部分，这是防抖与跟手性的常规取舍，目前值合理，不动也行。
- **目标清空不可发现**：改写时清空文字再回车 = 删除目标回到引导文字（`main.ts:217`，text 为空存 null）。功能存在但没有任何提示，用户多半靠猜。可在输入框 placeholder 上做文章（聚焦且已有内容时提示"清空后回车 = 删除"）。

## 与规格（CONTEXT.md/spec）的符合度抽查

| 规格要点 | 实现情况 |
| --- | --- |
| 周期更替目标自动清空（不清存储） | 符合：周期键不匹配即显示引导文字，存储不动（`dates.ts:104`） |
| 翻篇未完成任务滚入、颜色区分 | 符合：滚入琥珀橙两档制（`dates.ts:99`、`style.css:240`） |
| 已完成清单按日翻阅、单击修复回今日 | 符合（`archive.ts` 全篇），修复回来的按滚入色显示 |
| 一张便利贴 = 整个产品 | 符合，无双窗口；悬浮球是同一窗口的收起形态 |
| 存储层永不做清空动作 | 符合，代码里没有任何清空 archive/goals 的路径 |

结论：核心领域规则与规格高度一致，且都有单测护住（见测试篇）。
