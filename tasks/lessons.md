# lessons.md — 纠错经验沉淀

## 2026-09-11 · 样式从未接线，静默裸奔了九个里程碑

**发生了什么**：style.css 从 M3 写好起就没有任何 import/link 引用。Vite 只打包被引用的资源——不报错、不红屏、不挂测试，唯一症状是"UI 长得不对"。M8 验收把视觉项归为"待用户确认的主观项"，恰好给它放了行。

**规则**：

1. **改动渲染层样式后，验证对象是构建产物而不是源码**：`out/renderer/` 里必须存在 CSS 文件、`index.html` 必须含 `<link>`。源码存在 ≠ 产物存在。
2. **每个里程碑收尾必须看一眼运行中的窗口**（截图也算）。"逻辑全绿"和"用户看到的样子"是两条验收线，缺一不可。
3. TypeScript 7（tsgo）对真实存在的 CSS 文件做副作用导入会报 TS2882，通配 `declare module '*.css'` 压不住——用同目录 `style.css.d.ts` 解决。
4. 移植原型时先对齐"结构同构"再搬细节；原型里依赖模拟环境的部分（如 backdrop-filter 依赖假壁纸层）要替换成生产等价物（壁纸采样层），并在代码头注声明分叉原因。

## 2026-09-11 · 还原必须验合成结果

用户再次指出 UI 未还原原型。规则：不能以颜色变量一致替代视觉一致；必须验证背景层叠加顺序、窗口裁切和实际桌面截图。必须在相同背景、尺寸、内容下比较原型和实现；交互验收覆盖中文选字、草稿、长清单、连续完成、恢复后继续操作。

## 2026-09-11 · 原型视觉参数没在真实壁纸上验过

**发生了什么**：M10 按"用户当前壁纸适中"还原了原型的 saturate(1.5)、42% 白雾、大阴影参数；用户实际壁纸是高饱和亮色，便签直接糊成"亮青色块"、文字不可读、阴影光晕过大，三个问题一起爆发。原型参数是在原型自己的背景下调的，不等于在任意用户壁纸下成立。

**规则**：

1. 视觉参数凡"依赖背景内容"的（雾量、滤镜、对比度），交付前至少用一张高饱和亮色壁纸验一次可读性；做不到逐张验，就把参数做成随背景自适应，而不是写死。
2. 低不透明度文字（<0.4）必须声明其对背景的假设；没有自适应机制就默认会在亮背景上翻车。
3. 用户反馈"观感怪"时先问自己：这个效果在用户的真实环境（壁纸/其他窗口/缩放）里走一遍了吗？隔离环境里的"正确"不算数。

## 2026-09-11 · 全屏截图上直接读小字，凭空排查了一场假"数据回滚"

**发生了什么**：安装新版后在 2560×1440 全屏截图上直接辨认便签任务行，把 M14-1,2,5,6,7,8 看成了 M14-1…7 连号序列，与 data.json"对不上"，于是展开"数据被回滚"的排查——zoom 之后发现屏上文字与数据完全一致，排查对象根本不存在。低分辨率下大脑会按"M14-1 到 M14-7"的预期自动补全编号。

**规则**：

1. 凡要引用屏幕上的具体文字/数字作为事实依据（任务名、状态、按钮文案），必须先 zoom 放大到能逐字辨认再读；整屏截图只用于看布局，不用于读内容。
2. "屏上状态"和"落盘数据"对不上时，第一步先怀疑自己的读取得到的"屏上状态"，而不是先怀疑数据被改——前者靠 10px 文字辨认，后者是磁盘上的字节。
3. dev（app name `qink`）与正式版（`Qink`）的 userData 路径字符串不同，单实例锁互不感知，可同时运行，但数据都写 `文档\Qink\data.json`（后写覆盖先写）——排查数据问题前先 `tasklist` 确认只有一个实例在跑。

## 2026-09-11 · 悬停展开的胶囊超出窗口边界，被系统静默裁掉

**发生了什么**：球形态的悬停速记胶囊（宽 260 + 间隙 12）设计为从球侧滑出，但球形态窗口只有 168 宽（球 56 + 贴纸阴影边距 56×2）——胶囊 2/3 落在窗口外，Windows 直接裁掉不渲染，用户看到"输入框显示不全"。逻辑测试全绿、贴纸形态一切正常，唯独球形态的悬停态没人看过。

**规则**：

1. **窗口几何是和所有 UI 状态签的合同**：任何会出现的元素——包括悬停展开、聚焦滑出这类瞬态—— footprint 都必须算进窗口尺寸；只验证静态形态不算验证。
2. **每个形态（球/贴纸）都要单独看一眼运行中的窗口**，尤其是交互的目标形态本身；"默认形态没问题"不等于其他形态没问题。
3. 透明窗口的遮挡/裁剪类 bug，用系统无障碍树读元素边界（get_app_state full）能直接拿到几何证据：元素 bounds ⊆ 窗口 bounds 即无裁剪，比截屏更精确。
4. Windows 对透明无边框窗口的 GetWindowRect 会虚胖（本机 600×184 读成 660×203），判断窗口尺寸以主进程记账（noteSize）为准，别信读数。
5. 打包时报 EPERM rename dist\win-unpacked：是杀毒软件瞬时锁住刚写入的文件，删掉 dist\win-unpacked 重试即可，不是代码问题。

## 2026-09-11 · 坐标换算改了一半：拖动一启动就向左跳 216px

**发生了什么**：修速记胶囊裁剪时把 drag-move 的输出侧改成新边距（`pos.x - insetXForForm`），输入侧却还写着固定旧边距（`+ NOTE_INSET_X`）。球形态下两侧一加一减差 216px，长按拖动的第一帧窗口凭空左跳。贴纸形态两侧恰好同值所以无恙——只有球形态暴露。

**规则**：

1. **改坐标换算常量时，审计同管线的每一对加减**：grep 旧常量在该文件的剩余用法，逐处确认是否随形态/上下文取值，而不是只改触发本次 bug 的那一处。换算的输入侧和输出侧必须同源。
2. 「修好了 A 路径」的验证要通过 B 路径的实际操作（真实拖动）确认，同函数内的兄弟分支（note-resize）主动对齐，不留半新半旧。

## 2026-09-27 · 图标资产验证的两个环境坑

**发生了什么**:① GDI+ 生成的透明底 PNG glyph 在图片查看器里显示为一整块深色,险些误判资产坏了——实际是查看器把透明区合成在深色底上,alpha 直方图一量完全正确;② Git Bash 里 `taskkill /IM Qink.exe` 报"无效参数 - D:/Git/IM",MSYS 把 `/IM` 当 POSIX 路径转换了。

**规则**:

1. 验证带 alpha 的生成资产,不要依赖查看器的合成底色:用直方图统计 alpha 分布,或主动合成到白底/黑底各看一眼。"看起来坏了"可能是看的方式坏了。
2. Git Bash 调 Windows 原生命令,`/X` 风格参数一律写 `//X`(或走 `cmd //c`);遇到"无效参数"先怀疑路径转换再看语法。
3. 截图找窗口位置别信 data.json 原始坐标直接裁剪:noteX/noteY 是便签视觉坐标,窗口实际落点要减形态 inset(M14 教训的镜像面);先截整屏看布局再定裁剪区,裁剪矩形越界时 GDI+ 只报误导性的"内存不足"。

## 2026-09-11 · 200% 缩放屏上合成鼠标输入全部落空 + WorkerW 误判为遮挡

**发生了什么**：屏幕是 2560×1440 物理 / 200% 缩放（截图栅格 1280×720 即逻辑像素）。用 PowerShell SetCursorPos+mouse_event 做合成拖拽，坐标被系统按 DPI 虚拟化换算，点击全落在错误位置；WindowFromPoint 返回 WorkerW（桌面壁纸层）被我误读成「被其他窗口遮挡」，围着 Z-order 折腾了数轮。

**规则**：

1. 合成输入前先确认显示缩放；非 DPI-aware 进程（PowerShell 默认）发出的坐标是虚拟化逻辑坐标，与物理坐标差一个缩放系数。跨坐标系的工具（截图栅格/无障碍树/Win32 API/合成输入）必须先统一到同一空间再比对。
2. WindowFromPoint 返回 WorkerW/Progman = 空桌面，不是遮挡；判断遮挡要比对根窗口归属，且先认清各层身份再下结论。
3. 在用户活跃使用的桌面（窗口实时开合、200% DPI）上做合成拖拽验证不可靠：投入产出比急剧恶化时应止损，改为结构化代码验证 + 请用户实测。判断「验证不充分」和「验证环境不可行」是两回事。

## 2026-09-27 · executeJavaScript 的 DOM 引用回不来 + 既有验证脚本要整只抄

**发生了什么**：写 M15 端到端验证时，用 executeJavaScript 把菜单项元素返回到主进程再 `btn.click()`——DOM 元素经 IPC 序列化成空对象，报 `click is not a function`，脚本挂起。而同目录 task-pin-sort/verify.cjs 的既有手法（查找+点击整段作为字符串在页面内执行）本来就规避了这个坑。

**规则**：

1. executeJavaScript 的返回值必须可序列化（字符串/数字/布尔/纯 JSON）；要操作 DOM 就把整段逻辑作为字符串发进页面执行，只取结果标识回主进程。
2. 复用既有验证脚本时，执行模型（合成事件派发位置、元素引用处理）要整只继承，别自创变体——变体踩的坑往往正是原写法规避掉的坑。

## 2026-09-27 · 换 exe 图标后桌面快捷方式仍显示旧图（三层根因）

**发生了什么**：logo 全量替换并重装后，用户报告图标仍是旧的。取证：exe 本体图标已是新 Q，但桌面 lnk 是旧安装器遗留，且 Windows 图标缓存拿着旧图不放。先用温和方案（重建 lnk + `ie4uinit -show`）宣称修复，用户复测仍见旧图——温和刷缓存不够。

**规则**：

1. 「图标没更新」分三层查：exe 内嵌图标本体 → lnk 指向与 IconLocation → Windows 图标缓存。exe 新 ≠ 显示新。
2. 修复要彻底：有效组合 = 重建 lnk + 关 explorer + 删 `%LOCALAPPDATA%\IconCache.db` 与 `Explorer\iconcache_*.db` + 重启 explorer（`.scratch/task-due-time/fix-icon-cache.ps1` 可复用）。
3. 图标验证必须像素级，视觉模型对小图标两次判错（一次把未修复判成已修复）；可靠做法 = `Icon.ExtractAssociatedIcon().ToBitmap()` 统计暗色/琥珀像素占比。无头全屏采样要先排除窗口内容污染——贴纸的琥珀橙任务文字会让 amber 扫描全是假阳性。
4. 验证未通过前不要向用户宣布修复完成。

## 2026-09-27 · 形变动画的两类隐形杀手：中途测量读数与 min/max 托底

**发生了什么**：展开形变（球→贴纸）在真机上「吸附成硬切」。取证：`offsetWidth/offsetHeight` 的测量读数发生在元素可见后、起始帧前，强制了一次带过渡的样式重算——起始帧相对这次重算成了「变化」，自己触发过渡；目标帧设置时瞬间回弹，动画只剩零帧。另外 `#note` 的 `min-height:420px` 把 56px 起始/收束帧托成竖长条，形变两端根本变不成球。

**规则**：

1. **「隐藏→可见 + 起始帧 + 目标帧」的 FLIP 序列，测量读数必须在过渡被压制时完成**（探针阶段 `transition:none` → 落定起始帧 → 强制回流 → 恢复过渡 → 切目标帧）；可见状态下的任何布局读数都是一次样式重算，会把「下一帧才该生效」的值提前武装成过渡。
2. **形变端点值会被 min-/max- 托底**：写 `height:56px` 不等于渲染 56px 高。形变期间要临时解除 min-/max- 约束，清理时恢复。
3. 验证形变只能逐帧采样（rAF 里读 getBoundingClientRect），「起点/终点对了」不证明中间没跳；帧间位移上限按缓动峰值估（本例 460ms 走 216px → 帧差 ~32px，阈值 45px）。
4. 同管线成对换算的教训（M14）换个形态又犯了一次：`form-change` 输入侧用了新形态 inset。旧账规则不变：改任何「锚点/边距换算」时，grep 同管线的每一对加减，输入侧用「换算前形态」的口径。
